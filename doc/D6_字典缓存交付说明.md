## 〇.5、字典的作用（答辩讲稿）

### 字典是什么
把系统里"固定几个选项"的枚举值（保管期限、密级、档案状态等）从代码中抽离，统一放到 `sys_dict`（字典类型）+ `sys_dict_item`（字典项）两张表里管理。

### 解决什么问题
| 没有字典（硬编码） | 有字典 |
|---|---|
| 选项散落在后端代码/前端页面/数据库三处 | 选项只存在于字典表 |
| 加个"绝密+"要改代码重新部署 | 后台插入一条数据，零代码 |
| 改显示文案要动代码 | 改字典项，前端零改动 |

### 5 个核心作用
1. **存储与显示分离**：业务表只存编码（`permanent`），前端显示时查字典翻译成中文（"永久"）；改文案不动历史数据
2. **避免硬编码**：业务代码不写 `if(status==1)` 魔法数字，统一查字典，可读性可维护性提升
3. **运行时可维护**：新增/修改选项不需要改代码、不需要重启、不需要重新部署
4. **一处修改全局生效**：一个字典被多个模块引用，改一处所有地方同步
5. **多业务复用 + 一致性**：同一字典被多个模块共用，全系统对同一概念表述完全一致

### 实际使用链路
```
录入档案：前端下拉框 ← 查字典项(Redis缓存) → 选"机密" → 存库 da_file.security_level = "confidential"
查询档案：后端查库拿到 "confidential" → 前端查字典翻译成 "机密" 展示
```
Redis 缓存（方案A）优化的正是这个链路里最频繁的一环 —— 下拉框加载。

## 一、方案A思路（答辩讲稿）

### 为什么缓存字典
字典数据（保管期限、密级、档案状态）**几乎不改，但每次下拉框都要查**。
不缓存：10 次查询 = 10 次 MySQL；缓存后：1 次 MySQL + 9 次内存读取。

### 缓存工作流程
```
查询 → ① 查 Redis 缓存 → 命中 → 直接返回
                        ↘ 未命中 → ② 查 MySQL → ③ 回填缓存(TTL 30分钟) → 返回
```

### 三个经典问题的防护
| 问题 | 场景 | 对策 |
|---|---|---|
| 缓存穿透 | 查不存在的编码，缓存永远没有 | **空值也缓存**(TTL 5 分钟) |
| 缓存雪崩 | 大量 key 同时过期 | **TTL 随机抖动**(30 + 0~10 分钟) |
| 缓存一致性 | 改了字典缓存还是旧的 | **先改库后删缓存**，下次查询自动重建 |

### 缓存里存什么
- **KEY**：`dms:dict:{dictCode}`（如 `dms:dict:retention_period`）
- **VALUE**：该字典编码下**全部字典项列表**的 JSON 字符串（`List<SysDictItem>` 序列化）
- 字段说明：`id`(主键) / `dictId`(所属字典) / `itemCode`(编码,存库用) / `itemName`(名称,显示用) / `itemValue`(值) / `sort`(排序) / `status`(状态)
- Redis 只认字符串：存 = Java对象→JSON；取 = JSON→Java对象

## 二、方案B思路（Sa-Token token 存 Redis）

### 解决的问题
Sa-Token 默认把 token 存在**应用内存**，后端重启 → 内存清空 → 所有用户掉线重新登录。
方案B 把 token 存到 Redis → **后端重启不掉线**，用户无需重新登录。

### 实现
- pom 引入 `sa-token-redis-jackson`（排除自带 jedis，复用 spring-boot-starter-data-redis 的 Lettuce）
- 无需改代码，依赖引入后自动生效

### 验证结果
| 验证项 | 结果 |
|---|---|
| 登录后 token 写入 Redis | ✅ key = `Authorization:login:token:{token}` |
| token TTL | ✅ 2591846 秒 ≈ 30 天（符合 sa-token.timeout 配置） |
| **重启应用后旧 token 访问** | ✅ HTTP 200（方案B生效，重启不掉线） |

> 注意：key 前缀是 `Authorization`（因 sa-token.token-name 配置为 Authorization），不是默认的 satoken。

## 二.5、操作日志（@OpLog + AOP）

### 功能与作用
操作日志回答审计问题："**谁在什么时间、干了什么、结果如何**"。档案行业对操作留痕有合规要求，本模块用 AOP 切面自动记录，业务代码零侵入。

| 功能 | 作用 |
|---|---|
| 自动记录 | 标注 @OpLog 的接口，切面自动记录操作人/操作/参数/IP/耗时 |
| 成败皆录 | 成功和失败都记录（失败标记"（失败）"），方便排查问题 |
| 密码脱敏 | 参数里的 password 替换为 ***，明文密码永不入库 |
| 查询接口 | 管理员按操作人/操作描述分页检索历史 |

### 设计思路
在每个 Controller 的增删改方法上标注 `@OpLog("操作描述")`，由 **AOP 切面**自动拦截：
- 无需在每个方法里手写日志代码（解耦）
- 切面在方法执行后（finally）统一记录，**成功/失败都会记录**

### 记录内容
| 字段 | 来源 |
|---|---|
| user_id / username | Sa-Token 会话（登录时存入 username） |
| operation | @OpLog 注解 value |
| method | 类名.方法名 |
| params | 请求参数 JSON（**密码脱敏**为 ***） |
| ip | 请求头 X-Forwarded-For → 真实 IP |
| spend_time | 方法执行耗时（毫秒） |

### 设计要点
1. **参数脱敏**：`"password":"***"`，防止明文密码入库
2. **失败也记录**：finally 保证执行，失败标记"（失败）"
3. **日志失败不影响业务**：try-catch 包裹，落库异常只告警

### 测试结果
| 场景 | 结果 |
|---|---|
| 新增角色 → 日志 | ✅ userId/username/operation/params/ip/spendTime 完整 |
| 新增用户(带密码) → 日志 | ✅ 密码显示 `"password":"***"` |
| 删除用户成功 | ✅ 记录"删除用户" |
| 删除用户失败 | ✅ 记录"删除用户（失败）" |

## 六、注意事项

- Redis 密码不要写进 Git 提交的配置里（生产环境用环境变量）；本机密码仅用于开发
- 字典项增删改后**无需手动清缓存**，Service 层自动处理（先改库后删缓存）
- 前端下拉框数据源：`GET /api/system/dict/items/{dictCode}`
- 方案B 生效后，修改角色菜单等权限，用户需重新登录才能拿到新权限（token 会话缓存的权限码）
