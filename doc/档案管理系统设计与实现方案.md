# 一、项目定位与裁剪思路

原系统（同略数字档案，tl-szda）是一套面向政企单位的数字档案一体化管理平台（DAMS），支持纸质/电子档案的“收、管、存、用、鉴、销”全生命周期电子化管理。

本方案面向本科毕业生练手/毕设场景，在保留业务骨架的前提下，对技术栈进行降级，确保“一个人、30 天、可跑通、可演示”。

核心裁剪原则：

- 保留业务闭环：采集接收 → 整理编目 → 归档封库 → 保管 → 检索利用 → 鉴定 → 销毁。

- 砍掉企业级重武器：Activiti 工作流引擎、Solr 全文检索、ShardingSphere 分库分表、Nacos 配置中心、XXL-JOB 任务调度、RabbitMQ 消息队列。

- 技术降级：用 Spring Boot + MyBatis-Plus + Sa-Token + MySQL 作为主体，Vue 3 + Element Plus 作为前端。

- 保持行业属性：全宗/门类/案卷/文件层级、档号自动生成、逻辑删除、生命周期履历等档案行业特色功能完整保留。

# 三、功能方案

系统功能分为“核心业务闭环”与“配套支撑功能”两大部分。

## 3.1 核心业务闭环（立身之本）

档案层级：全宗 → 门类 → 案卷 → 文件（比原系统砍一层“项目”，够用且不冗余）。

生命周期：采集接收 → 整理编目 → 归档封库 → 保管 → 检索利用/借阅 → 鉴定 → 销毁。

- 全宗管理：全宗 CRUD，一个全宗对应一个立档单位（如“计算机学院”）。

- 门类管理：档案门类（文书/科技/会计/声像）及著录字段配置。

- 采集接收：单条著录、原文上传、Excel 批量导入。

- 整理编目：档案列表、编辑元数据、档号自动生成。

- 归档封库：状态流转“整理中 → 已归档 → 已封库”，封库后只读。

- 检索利用：多条件组合查询（题名/档号/关键词/年度/门类/保管期限/密级）、分页排序。

- 借阅管理：借阅申请 → 管理员审批（通过/驳回）→ 在线浏览原文 → 归还登记。

- 鉴定销毁：到期档案清单、鉴定登记（续存/销毁）、销毁记录（逻辑删除）。

- 生命周期履历：每一步状态变更写一条履历，详情页用时间轴展示。

## 3.2 配套支撑功能（撑起系统完整度）

- 系统管理：用户/角色/菜单（按钮级权限）、字典管理。

- 操作日志：AOP 注解记录“谁在什么时间干了什么”。

- 数据权限：普通管理员按 fonds_id 过滤数据。

- 统计报表：首页驾驶舱（档案总数、门类分布饼图、年度趋势折线、借阅排行 Top10）。

- 到期提醒：@Scheduled 每天扫描保管期限到期档案，首页提示。

- 库房管理（可选）：库房 → 密集架 → 单元格三级 CRUD，档案关联存放位置。

# 四、数据库设计（核心表）

共约 15 张核心表，按“系统管理、档案核心、业务流转”三大域组织。

## 4.1 系统管理域

- sys_user：用户（id, username, password, real_name, role_id, fonds_id, status）

- sys_role：角色（id, role_name, role_code）

- sys_menu：菜单/权限（id, parent_id, name, type, perms, path）

- sys_role_menu：角色-菜单关联

- sys_dict：字典（保管期限、密级、档案状态等枚举）

- sys_log：操作日志（user_id, operation, method, params, ip, create_time）

## 4.2 档案核心域

- da_fonds：全宗（id, fonds_code, fonds_name）

- da_archive_type：门类（id, type_code, type_name, fonds_id）

- da_volume：案卷（id, fonds_id, type_id, volume_no, title, year, retention_period, security_level, status）

- da_file：文件/档案（id, volume_id, archive_no, title, author, doc_date, year, retention_period, security_level, keywords, pages, status, fonds_id, type_id, del_flag, create_by/time, update_by/time）

- da_electronic_file：电子原文（id, file_id, file_name, file_path, file_size, file_type, upload_time）

- da_lifecycle：生命周期履历（id, file_id, action, operator, detail, create_time）

## 4.3 业务流转域

- da_borrow：借阅单（id, file_id, applicant_id, reason, apply_time, status, approver_id, approve_time, approve_comment, return_time）

- da_appraisal：鉴定记录（id, file_id, result, reason, operator, create_time）

- da_destruction：销毁记录（id, file_id, destruction_no, reason, operator, approve_id, create_time）

关键设计点：

- 档号生成：全宗号-门类代码-年度-四位序号，序号采用“该年度最大序号+1”，加事务防并发重复。

- 逻辑删除：所有档案表带 del_flag，销毁也是状态流转而非 DELETE，符合档案行业“留痕”要求。

- 生命周期履历：每次状态变更插一条记录，详情页用时间轴组件展示，低成本高回报。

4.6 数据库关系设计详解

4.6.1 四大域划分

系统 19 张表按业务边界划分为四大域，各司其职：

| 域 | 包含表 | 职责 |
| --- | --- | --- |
| 系统管理域 | sys_user、sys_role、sys_menu、sys_role_menu、sys_dict、sys_dict_item、sys_log | 管"谁能用"：账号、角色、菜单权限、字典、操作日志 |
| 档案核心域 | da_fonds、da_archive_type、da_volume、da_file、da_electronic_file、da_lifecycle | 管"档案怎么存"：四级组织层级 + 电子原文 + 生命周期履历 |
| 业务流转域 | da_borrow、da_appraisal、da_destruction | 管"档案经历了什么"：借阅、鉴定、销毁 |
| 库房管理域 | da_warehouse、da_shelf、da_cell | 管"档案放哪"：实体档案的物理定位 |

4.6.2 档案核心层级：全宗 → 门类 → 案卷 → 文件

该四层结构符合国家档案行业标准（DA/T 系列）的档案组织方式，是档案系统的骨架：

| 层级 | 表名 | 含义 | 业务示例 |
| --- | --- | --- | --- |
| 全宗 | da_fonds | 一个立档单位（档案主体） | JSXY 计算机学院、ZW 组织部 |
| 门类 | da_archive_type | 全宗下的档案分类 | WS 文书档案、RS 人事档案 |
| 案卷 | da_volume | 一组关联文件的组合 | 2026 年度文书卷 |
| 文件 | da_file | 最小的档案实体 | 一份通知、一份合同 |

层级之间的外键关系：da_archive_type.fonds_id → da_fonds.id；da_volume.type_id → da_archive_type.id；da_file.volume_id → da_volume.id。

档号规则与层级一一对应：档号 = 全宗号 - 门类代码 - 年度 - 四位序号（如 JSXY-WS-2026-0001）。从档号可反推"哪个全宗、哪个门类、哪一年、第几份"，档号即档案的"身份证"，全国通用。

4.6.3 数据权限：用户为何关联全宗

sys_user 表通过 fonds_id 字段关联 da_fonds（全宗），这是系统的核心安全机制：

业务场景：计算机学院（全宗 A）的管理员只应管理本学院的档案，不应看到组织部（全宗 B）的档案。

实现方式：用户登录后，系统查询档案时自动追加 WHERE fonds_id = 当前用户.fonds_id 条件，实现数据隔离。

超级管理员例外：fonds_id 为空（不归属任何全宗）的超级管理员可查看全部数据。

该设计实现了"身份权限（角色）+ 数据权限（全宗）"的双重隔离，是企业级档案系统的必备能力。

4.6.4 关键关联设计决策

da_file 冗余 fonds_id + type_id（反范式设计）：档案查询 90% 按全宗筛选，若从 file → volume → type → fonds 逐级 join，每次查询跨 4 张表。冗余这两个字段后单表即可完成筛选，用空间换性能。

业务单据存"人名字段"快照：da_borrow 同时存 applicant_id + applicant_name、approver_id + approver_name。审批通过后再查用户表可能用户已删/改名，单据上必须保留当时快照，保证"留痕"。

da_lifecycle 独立生命周期履历表：档案"归档 → 封库 → 借阅 → 归还 → 鉴定 → 销毁"每一步记一条履历（动作、操作人、时间、详情），相当于档案的"病历本"，任何时刻可追溯完整历史，符合档案合规要求。

库房三级物理定位：da_warehouse（库房）→ da_shelf（密集架）→ da_cell（单元格），da_file 存 cell_id，可回答"档案实体放在哪一排哪一格"。

sys_role_menu 关联表处理多对多：一个角色拥有多个菜单，一个菜单也属于多个角色，用中间关联表而非在单表存列表。

4.6.5 外键约束策略

数据库脚本末尾提供了外键 DDL（sys_user→sys_role、sys_user→da_fonds、sys_role_menu→sys_role/sys_menu、sys_dict_item→sys_dict），但标注为可选。原因：

MyBatis-Plus 逻辑删除（del_flag）与外键同时启用时，删除前必须先处理关联数据，否则外键会阻止逻辑删除的 UPDATE 语句；

本项目数据一致性优先在应用层（Service 层校验，如"角色下有用户禁止删除"）保证，外键作为兜底保护可选择性启用。

# 五、代码规范（借鉴原系统好习惯）

- 统一返回体 Result<T>：{code, msg, data}，配全局异常处理 @RestControllerAdvice。

- 分层：Controller（薄）→ Service/ServiceImpl → MyBatis-Plus BaseMapper，不写 XML。

- MyBatis-Plus 三件套：LambdaQueryWrapper 拼条件、Page 分页、MetaObjectHandler 自动填充 createTime/updateTime。

- 操作日志 AOP：自定义 @OpLog 注解 + @Aspect 切面落库，不在业务代码里手写日志。

- 入参校验：DTO 加 @NotBlank 等 + @Validated，非法参数直接 400。

- 前后端分离：后端只出 JSON，前端 axios 拦截器统一处理非 200 响应。

# 六、每日开发计划（30 天，每天 3~5 小时）

按“每周一个里程碑”设计，每周末留出缓冲。若某天未按时完成，顺延到缓冲日，不压缩测试时间。

- D2：集成 MyBatis-Plus + 分页插件；写统一返回 Result、全局异常、公共字段自动填充；用代码生成器生成第一套 CRUD 跑通。

- D3：建 5 张系统表；集成 Sa-Token，完成登录/登出/获取用户信息接口；密码 BCrypt 加密。

- D4：用户管理 CRUD + 角色管理 CRUD + 给用户分配角色。

- D5：菜单管理 + 角色分配菜单；登录后返回当前用户的菜单树和权限码；@SaCheckPermission 按钮级权限。

- D6：字典管理 + 操作日志 AOP（@OpLog 注解 + 切面落库）。

- D7：缓冲 + 前端起步：初始化 Vue3+Vite+Element Plus 工程，做登录页和主布局，联调登录，菜单按权限动态渲染。

## 第 2 周：档案核心（目标：档案能著录、能上传、能查）

- D8：全宗管理、门类管理（前后端）。

- D9：档案树：左侧“全宗→门类→年度”树组件，点击节点过滤右侧列表。

- D10：案卷表 + 文件表建表；档号生成逻辑（事务 + 最大序号+1）；文件著录接口。

- D11：著录表单页（题名/责任者/日期/保管期限/密级/关键词等）；案卷-文件从属关系。

- D12：电子原文上传（限制类型/大小，存本地磁盘按 年/月 分目录），档案详情页展示原文列表。

- D13：Excel 批量导入（Hutool：上传→逐行校验→错误行反馈）；原文在线预览（pdf 用浏览器/pdf.js，图片直接展示）。

- D14：缓冲 + 联调：把第 2 周功能串一遍（著录→上传→树过滤→详情），修 bug，补操作日志注解。

## 第 3 周：生命周期流转 + 借阅（目标：业务闭环跑通）

- D15：状态流转：整理中→已归档→已封库（按钮按状态显隐，封库后禁止编辑）；生命周期履历表 + 详情页时间轴展示。

- D16：检索页：多条件组合查询（题名/档号/关键词模糊 + 年度/门类/保管期限/密级下拉）+ 分页 + 排序。

- D17：借阅申请：检索结果“申请借阅”按钮→填写理由→生成借阅单（待审批）。
