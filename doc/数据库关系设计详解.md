# 数据库关系设计详解

> 对应设计文档《档案管理系统设计与实现方案》第 4.6 节
> 项目：Document Management System（档案管理系统 · 本科毕业设计）

---

## 一、四大域划分

系统 19 张表按业务边界划分为四大域，各司其职：

| 域 | 包含表 | 职责 |
| --- | --- | --- |
| 系统管理域 | sys_user、sys_role、sys_menu、sys_role_menu、sys_dict、sys_dict_item、sys_log | 管"谁能用"：账号、角色、菜单权限、字典、操作日志 |
| 档案核心域 | da_fonds、da_archive_type、da_volume、da_file、da_electronic_file、da_lifecycle | 管"档案怎么存"：四级组织层级 + 电子原文 + 生命周期履历 |
| 业务流转域 | da_borrow、da_appraisal、da_destruction | 管"档案经历了什么"：借阅、鉴定、销毁 |
| 库房管理域 | da_warehouse、da_shelf、da_cell | 管"档案放哪"：实体档案的物理定位 |

---

## 二、档案核心层级：全宗 → 门类 → 案卷 → 文件

该四层结构符合国家档案行业标准（DA/T 系列）的档案组织方式，是档案系统的骨架：

| 层级 | 表名 | 含义 | 业务示例 |
| --- | --- | --- | --- |
| 全宗 | da_fonds | 一个立档单位（档案主体） | JSXY 计算机学院、ZW 组织部 |
| 门类 | da_archive_type | 全宗下的档案分类 | WS 文书档案、RS 人事档案 |
| 案卷 | da_volume | 一组关联文件的组合 | 2026 年度文书卷 |
| 文件 | da_file | 最小的档案实体 | 一份通知、一份合同 |

层级之间的外键关系：

- `da_archive_type.fonds_id` → `da_fonds.id`
- `da_volume.type_id` → `da_archive_type.id`
- `da_file.volume_id` → `da_volume.id`

档号规则与层级一一对应：

**档号 = 全宗号 - 门类代码 - 年度 - 四位序号**（如 JSXY-WS-2026-0001）

从档号可反推"哪个全宗、哪个门类、哪一年、第几份"，档号即档案的"身份证"，全国通用。

## 三、数据权限：用户为何关联全宗

`sys_user` 表通过 `fonds_id` 字段关联 `da_fonds`（全宗），这是系统的**核心安全机制**：

- **业务场景**：计算机学院（全宗 A）的管理员只应管理本学院的档案，不应看到组织部（全宗 B）的档案。
- **实现方式**：用户登录后，系统查询档案时自动追加 `WHERE fonds_id = 当前用户.fonds_id` 条件，实现数据隔离。
- **超级管理员例外**：fonds_id 为空（不归属任何全宗）的超级管理员可查看全部数据。

该设计实现了"身份权限（角色）+ 数据权限（全宗）"的双重隔离，是企业级档案系统的必备能力。

## 四、关键关联设计决策

1. **da_file 冗余 fonds_id + type_id（反范式设计）**
   档案查询 90% 按全宗筛选，若从 file → volume → type → fonds 逐级 join，每次查询跨 4 张表。冗余这两个字段后单表即可完成筛选，用空间换性能。

2. **业务单据存"人名字段"快照**
   `da_borrow` 同时存 `applicant_id + applicant_name`、`approver_id + approver_name`。审批通过后再查用户表可能用户已删/改名，单据上必须保留当时快照，保证"留痕"。

3. **da_lifecycle 独立生命周期履历表**
   档案"归档 → 封库 → 借阅 → 归还 → 鉴定 → 销毁"每一步记一条履历（动作、操作人、时间、详情），相当于档案的"病历本"，任何时刻可追溯完整历史，符合档案合规要求。

4. **库房三级物理定位**
   `da_warehouse`（库房）→ `da_shelf`（密集架）→ `da_cell`（单元格），`da_file` 存 `cell_id`，可回答"档案实体放在哪一排哪一格"。

5. **sys_role_menu 关联表处理多对多**
   一个角色拥有多个菜单，一个菜单也属于多个角色，用中间关联表而非在单表存列表。

---

## 五、外键约束策略

数据库脚本末尾提供了外键 DDL（sys_user→sys_role、sys_user→da_fonds、sys_role_menu→sys_role/sys_menu、sys_dict_item→sys_dict），但标注为**可选**。原因：

- MyBatis-Plus 逻辑删除（del_flag）与外键同时启用时，删除前必须先处理关联数据，否则外键会阻止逻辑删除的 UPDATE 语句；
- 本项目数据一致性优先在**应用层**（Service 层校验，如"角色下有用户禁止删除"）保证，外键作为兜底保护可选择性启用。
