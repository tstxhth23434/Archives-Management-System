> 日期：2026-08-14

## 〇、功能与作用（设计思路）

### 菜单/权限在系统里的位置
D4 建好了用户和角色，D5 回答"**每种角色能看到什么、能操作什么**"。这是权限体系的核心落地：菜单树决定侧边栏显示哪些页面，权限码决定按钮是否可见、接口是否放行 —— 前后端双重控制。

### 三级权限体系（答辩重点）

```
① 登录拦截    → 未登录 401（D3 完成，所有接口的通行证检查）
② 按钮级权限  → @SaCheckPermission 注解，无权限 403（本模块核心）
③ 数据权限    → fonds_id 过滤（已设计，D8 档案业务落地）
```

### 各功能的作用

| 功能 | 作用 |
|---|---|
| 菜单树管理 | 维护目录/菜单/按钮三级结构，前端据此渲染侧边栏 |
| 角色分配菜单 | 给角色勾选可见菜单和可操作按钮（先删后插，事务保证） |
| 用户菜单+权限码 | 登录后返回该用户可见的菜单树和权限码列表，前端动态渲染 |
| 按钮级权限 | `@SaCheckPermission("system:user:delete")` 拦截无权限的接口调用 |

### 核心设计决策（答辩要点）

1. **菜单三种类型**：目录(顶级分组) / 菜单(可访问页面) / 按钮(操作权限码) —— 从"能看什么"细化到"能点什么"
2. **权限码来源**：用户 → 角色 → 角色菜单关联 → 菜单 perms 字段，由 `StpInterfaceImpl` 实时从数据库加载
3. **注解式鉴权**：`@SaCheckPermission` 加在接口上，一处注解一处生效，业务代码零侵入
4. **动态菜单**：前端不写死菜单，登录后调 `/api/auth/menus` 拿菜单树渲染 —— 换角色立即换界面
5. **权限码与会话**：权限码缓存在登录会话中，修改角色菜单后用户需重新登录生效

| 接口 | 方法 | 路径 | 说明 |
|---|---|---|---|
| 菜单树 | GET | `/api/system/menu/tree` | 全量树形结构（管理端） |

| 分配菜单 | POST | `/api/system/role/{id}/menus` | 先删后插，事务 |

### 当前用户（`/api/auth`）

| 接口 | 方法 | 路径 | 说明 |
|---|---|---|---|
| 用户菜单+权限码 | GET | `/api/auth/menus` | 返回 { menus: 菜单树, perms: 权限码列表 } |

## 三、权限体系（三级）

1. **登录拦截**：所有 `/api/**`（除白名单）需登录，未登录返回 401
2. **按钮级权限**：`@SaCheckPermission("system:user:delete")` 注解，无权限返回 403
   - 权限码来源：用户角色 → 角色菜单关联 → 菜单 perms 字段
   - 由 `StpInterfaceImpl` 从数据库实时加载
3. **数据权限**：fonds_id 过滤（D4 已设计，D8 档案业务时落地）

## 五、使用说明

1. 执行 `doc/database/init_menu.sql` 初始化菜单（已执行）
2. 重启应用，`doc.html` 新增"04-菜单管理"分组
3. 登录 admin，调用 `GET /api/auth/menus` 可看到菜单树+权限码（前端据此渲染侧边栏+控制按钮）

## 六、注意事项

- 前端动态菜单：登录后调 `/api/auth/menus` 拿菜单树渲染侧边栏，按 perms 控制按钮显隐（D7 前端实现）
- 修改角色菜单后，用户需**重新登录**才能生效（权限码在登录会话中缓存）
- `sys_role_menu` 表无 del_flag，删除菜单时同步删除关联
